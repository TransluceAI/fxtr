current system:
- scopes need to ensure that they only live as long as the lifetime of any external arenas that are mounted into them unsafely, so that we maintain the closed subgraph invariant
- right now we do this by allocating a new memory store to every scope, and having scopes use inheritance parents to reference each other
- then the scopes additionally layer a lifting mechanism on top of this
- however the arenas/stores don't know about the scope lifting, and instead just copy data until the store knows how to find everything; it can't "re-adopt" external arenas even if it knows they exist
- this leads to awkward properties when you try to move data "up" the scope tree (from a child to a parent or sibling) where you may pay end up loading a lot of stuff into memory unnecessarily
- also there is overhead due to having a totally separate memory store for every scope
- also there is no way to offload data back into a remote store; once it is in memory it just stays there forever

idea for a new system:
- move everything into a single global memory store
- however, that memory store _virtually_ tracks multiple "lifetime tokens" and acts as if it has a separate set of known entities for each
- a single "lifetime token" corresponds to the lifetime of an external resource, and we create a new lifetime token every time we open an external resource scope. each arena is tied to a lifetime token. lifetime tokens have parents, which are other lifetime tokens; parent lifetimes are always longer than child lifetimes.
- instead of a fixed set of states (derived, stored, inherited) each entity node in the memory store instead tracks a number of things:
    - optionally, its in-memory loaded data
    - optionally, a mapping from lifetime token to an inheritance arena that is responsible for this data in an external resource. can co-exist with in-memory loaded data.
    - implicitly or explicitly, a set of lifetime tokens that have a claim to this node.
        - in order for a lifetime token to have a claim to a node, at least one of three cases must be true:
            - case 1: some parent lifetime token also has a claim to this node
            - case 2: this lifetime token has an inheritance arena registered for this node
            - case 3: this node has in-memory loaded data, and for every dependency of the node, this lifetime token has a claim on that dependency
        - possibly, the right representation of this is as an _antichain_ of lifetime tokens that are known to have a claim on the node (from which we can compute the full set), where at the time we add a token to the antichain for a node, we either know case 2 holds or case 3 holds; then case 1 is free.
        - as an optimization, if some token is not part of the antichain, we could drop it from the token-to-inheritance-arena map, because there is already a longer-lifetime lease that guarantees access to it
        - it is possible for a claim to be grounded in both case 2 and case 3; for now we will just allow both to be true. in the future we could either clean up the case 2 claim to avoid depending on the resource, or offload 3 back to 2 to save memory.
- each arena is associated with one lifetime token. for an entity to be in the arena, its lifetime token must have a claim to the node
- when we _load_ a node in an arena:
    - if that node is already in memory, we should already satisfy the constraints, so we can just track the deps and return it
    - if the node is _not_ already in memory, we need to pick one of the lifetime tokens in the antichain that is an ancestor of this one and that has an inheritance arena, and load the entity from it. we then propagate just that antichain token into the loaded node's children (which would point to the same inheritance arena, which now contains the deps)
- when we _store_ a node in an arena:
    - the data gets stored in memory
    - for lifetime, the high level idea is that we want to propagate the longest lifetime that this arena "knows about" and can verify.
    - this means we essentially want to take the intersection of (a) all of the implicit claim sets (downwardly closed) of all of the nodes being stored, (b) the arena's token's ancestor set.
    - if we already have this node, this new set gets added into the set of lifetime claims on the node
- dealing with external resources:
    - external resources correspond to some token, and are guaranteed to live at least as long as the token
    - they can be mounted into the store by attaching them to a node that does not already have a claim for that token, and attaching an inheritance arena derived from the resource; at this point they can now be tracked in any arena that has or depends on that token
- how scopes fit in
    - scopes should mostly have the same API that they already do, from the user's perspective
    - however, they should no longer track a store, instead they should just have their main arena, and the main arena should have a token
    - in the full system, there should be two types of scope, determined at creation time:
        - some scopes inherit the same lifetime token as their parent scope. this only works if all parent scopes have the same lifetime token, _and_ if they were not constructed via an internal helper that declares they need to have a new lifetime token
        - any scope that has parents with different lifetime tokens, or that is annotated as needing its own lifetime token, acquires a new one, which it then "owns".
        - if a scope owns its lifetime token, then when it closes, it closes the lifetime token in the memory store. this then removes all claims for that lifetime token, and deletes any node that now has no claims, since that node is no longer loadable. (this implies we have to track the set of nodes that each lifetime token is in the antichain for.)
    - temporarily, we can make it so that every scope creates its own token, similar to how right now every scope creates its own store
- sync `track_from_scope` operation, similar to async `copy_from_scope` operation
    - new operation on scopes, possibly backed by a new operation on specifically the memory arena
    - what it lets you do is synchronously re-claim a node from scope A (and its arena) into scope B (and its arena)
    - how it works: it walks the DAG of nodes rooted at the given node in the memory store, and tries to re-claim them for the target arena's lifetime
        - when it finds a node that is already claimed in the target arena's lifetime, it stops; we are done
        - otherwise, for any node that has storage in memory, it tries to re-claim all of its dependencies. if it succeeds, it then also claims the node itself, as if it had stored the node, but without doing any serialization or tracking it in the arena, just propagating lifetimes
        - otherwise, if it has reached a node that is _not_ in memory and is _not_ claimed in the target arena's lifetime, that means that we can't safely track this node, because it depends on an external resource that is not known to be available in the target arena's lifetime. this then becomes an error raised up to the `track_from_scope` caller.
    - use case: build up a value in a sub-scope, then "transfer" the result back out into a parent scope, under the assumption that it is safe to transfer.
- bonus feature: "weak scope"
    - a weak scope is like a regular scope except (a) it has exactly one parent scope and _must_ have exactly the same lifetime token as its parent scope, (b) it does _not_ hold a keep-alive on its parent, but instead has the reverse: it puts itself on a list on its parent and, when its parent closes, it closes also.
    - proper child scopes can still inherit from a weaks cope, and will keep the scope alive, but they do so by registering a keep-alive on the non-weak parent of the weak scope (or, generally, following up the weak parent chain until reaching a non-weak scope)
    - can be added later, after the rest of the system
