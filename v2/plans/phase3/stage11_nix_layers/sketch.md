the idea would be that nix flakes would handle all of the building and configuration, and my system would be the runtime and lazy-loading service layer that sits on top.
- high level
    - we'll assume there is a floating "remote entity store" that will be available at runtime, that can fetch entities by their FxtrID. this will be configured by the user. we don't have to worry about the state of this very much because everything is content addressed, but we will need it to be there in order to lazily resolve references at runtime.
    - we'll then have some nix flakes, which sit on top of the remote entity store and (a) build new entities, (b) define manifest objects that refer to new entities, (c) compile binary artifacts that depend on entities and/or should be saved back into entities
        - these nix flakes can retrieve entities from the remote entity store via a fixed-output-derivation that "preloads" entity data into the store. we are allowed to preload to arbitrary depth; things that were not preloaded stay as "remote references" that have to be resolved later at runtime rather than at build time. anything that has been preloaded is additionally available at build time.
        - initially, we can prototype this by having a few types of derivation:
            - fixed-output derivations that just preload data, pointing at a hardcoded localhost URL that is expected to serve entity data via the HTTP interface, and then use `lib.fakeHash` to capture hash on first use
            - normal input-addressed derivations that depend on the preload derivations and each other, and just store new entities
        - eventually we'll do this via a helper nix function that reads from a `fxtr_imports.toml` and a `fxtr_imports.lock`
    - we'll then have "a folder with a root nix flake" as the "canonical" way of referring to all of these:
        - first you write your nix flakes to preload any data you need and then define your core entity types and transformations
        - then you use `nix build` to build the outputs, which creates some stored entity data as files in the nix store
        - then you open those files using fxtr2 logic that can walk them and expose them via the existing APIs
        - if that logic then gets to an ID that was marked as "in the remote store", it then reroutes to the remote store and loads that entity + its transitive dependencies from there instead
- to encode this, we'll have some sort of "layered file entity store" concept on top of this. this will essentially be a convention for representing "layers" of new entities on top of a remote entity store.
    - a layered file entity store will have three parts:
        - a JSON object of "pins", which map human-readable keys to FxtrIDs,
        - a JSON object of "parents", which are a list of abspaths to other layered file entity stores
        - a folder of data, addressed by FxtrID and containing CBOR-encoded entity flat data (in a similar format as is returned by the experimental HTTP server)
        - a folder of precomuted metadata, addressed by FxtrID, for pinned IDs that are remote and do not appear in the flat data dir
            - note that the remote location itself does NOT appear here; it is supposed to be configured at runtime
    - the interpretation of a layered file entity store is:
        - the dir itself and the initial parents give you a search set
        - the pins tell you what data is expected to be here
        - if you load data from one of the parents, you should add the parents of that parent to the active search set when loading children of it
        - if you don't find data in the search set, it is assumed to be in the remote store
    - the purpose of the "layered file entity store" is to bridge the world of fxtr entities into and out of nix. when running inside nix, a program can load any data that is stored in this derivation's store path, or load any data that was stored in any _input_'s layered stores. it can then save the results into its own derivation's store path and produce those as its normal build artifacts.
        - when running in the nix sandbox, outside of fixed-output-derivation land, we will not be able to access entities that are expected to exist in the remote entity store. so, the expectation will be that any remote entities we need have already been prefetched by some fixed-output derivation.
            - if you try to load one of these when running in a nix sandbox, you'll get an error saying that the remote entity store is not accessible during isolated builds and you need to prefetch any entities you will load during build
        - but: any other entities that those prefetched entities _link to_ will still just contain tagged remote pointers. this is fine in nix. after build time, when we load these in a dynamic running program, we can load through to those linked entities by following that pointer outside the sandbox
        - then there will be some sort of bridge step where we run a fixed-output-derivation that fetches from some remote namespace, preloads some subset of entities as needed, and writes their data out into the layered entity store file structure
            - with eventually some nix tooling around it
    - the layered file entity store will be in a submodule of fxtr2.data .
        - it will be sort of like a namespace but it will have somewhat different rules
        - there will be two classes, `LayeredFileStoreReader` + `LayeredFileStoreIsolatedWriter`.
        - for `LayeredFileStoreReader`:
            - read-only
            - it is essentially a subclass of FxtrReadNamespace, letting you load entities
            - takes a directory as input, and an optional remote entity store config telling it how to resolve remote entities
            - its scope acts like the HTTP namespace's scope, and can freely inherit from other scopes and be used like normal
            - its arenas each track a search set that they should use to find data
            - this is intended to be used from arbitrary Python code that wants to interface with a written store
        - for `LayeredFileStoreIsolatedWriter`:
            - write-only
            - takes a directory where it will write output, an optional remote entity store config telling it how to resolve remote entities, and a list of parent layer directories it will be a layer on top of
            - does not have any scope.
            - it has methods:
                - `mark_as_remote(entity_id)`: mark an entity as required to be in the remote store
                - `pin_to_this_layer(name, entity_id, from_scope)`: pin an entity from this writer's scope into its own pin list. this also walks and saves referenced entity data (starting from this one and walking through linked entities) until it reaches an entity that already exists in this layer or some parent (either as data or as a remote reference)
                - `preload_data(entity_id)`: make sure that this entity has data on disk in either this layer or some parent layer, NOT just a remote reference. this entity must already exist in this layer or some parent (either as data or as a remote reference). if remote, load it from the remote, save the data, and mark as a remote reference every dep entity that appeared in the loaded data that was not already known to one of our parents.
- once we have this, we'll prototype a flow that uses nix to augment some existing entities with new entities
    - a script which stands up a HTTP server serving a few nested known entities, as our "fake remote store"
    - a nix flake which has a FOD that preloads some but not all of these entities (e.g. the first two items in a linked list)
    - a nix flake which is pure, that runs python to load some entities from the first FOD, then add new things on top (e.g. branching the linked list partway down, then adding new elements to the end)
    - a script which uses nix to build the flake(s) and then deeply loads all of the entities they stored or referenced, including ones that were kept remote and not preloaded, but rerouting the remote store entities to its own source for them rather than assuming that the original HTTP server is still up
