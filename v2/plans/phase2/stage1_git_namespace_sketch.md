Plan for layering git semantics on top of the Fxtr store.

Fxtr is developing the concept of a “(name)space” (or maybe “repo”?): a place where

* entities are pinned
* arenas can exist
* backrefs can be followed

Two existing spaces:

* Memory space / memory store: A pure Python space. Holds objects as Python in memory.
* Sqlite store namespace: A layer in a sqlite store. Allows objects to be pinned by name. Stores all the objects in a backing store and tracks backrefs per db.

Disadvantage to sqlite store: although persistent, it does not allow version control.

New idea: Git repo space, layering with a sqlite mirror.

Idea:

* Git repo files are source of truth for namespace pins, and identifies what is in the namespace via content hash IDs
* Sqlite is a mirror of Git state and also stores the actual content pointed to by the IDs
* Sqlite db maintains backrefs and consistency properties
* Git is extended so that this sqlite state is transferred along with the filesystem state, kind of like how git lfs works, but simpler because we don’t actually “smudge” the files on the filesystem

More specific:

* Representation
  * Files in git: .fxtr.tsv
    * TSV with sorted keys and fxtr IDs, represents map “{path}:{key}” in namespace pin. Does not allow tabs in keys.
  * Sqlite mirror
    * worktree namespace: mirrors a current worktree and uses the same “{path}:{key}” keys
    * index namespace: holds all refs needed by any git version
* Syncing tools:
  * worktree sync: given a new git checked-out state, migrate from index namespace to worktree namespace, or error if we see any nodes we don't recognize. Cache so that repeated sync is fast
  * pull sync: given an incoming git pack OR a checked-out state, find all referenced IDs, pull from a remote arena into index namespace
  * push sync: given an outgoing git pack, create an arena with all referenced IDs
* Python interface
  * Namespace ABC implementation like the sqlite namespace. But:
    * On read, first do a worktree sync, then read from sqlite
    * On copy into:
      * copy into backing index store sqlite
      * write into worktree
      * worktree sync \=\> pulls it into the sqlite checkout mirror
    * All returned arenas just end up being arenas into the mirror namespace
* Git interface
  * Internal Repo or user config
    * default location of the sqlite store on the computer
  * gitignored config (generated if needed)
    * uuid of the index sqlite namespace
    * uuid(s) of the worktree mirror namespace(s)
    * override location of the sqlite store on the computer
  * Versioned repo config files
    * Custom merge driver config
    * Location of fxtr store root(s)
  * Custom protocol to intercept packs
    * git-protocol-fxtr
    * combines a git URL and a fxtr server URL
    * Runs syncs in both directions as needed
  * Custom merge driver
    * Merges .fxtr.tsv files by sorting as maps
  * Optional precommit
    * Makes sure fxtr values are tracked, prompts to run a manual fxtr pull to restore mirror

Executing the code already gives us this, there's nothing to do. We can't pin anything anyways. Perhaps as a convenience feature we allow some top-level exporting or walking of modules.)

Simpler version of this to start, without requiring custom git pack system:

* Full data representation in tsv \+ sqlite backing store
  * Some `fxtr_store.toml` file that identifies a given subdir as a fxtr-store namespace
  * Gitignored configurations set up to identify where the backing store is on the user’s computer and what namespace UUIDs it uses
* Python namespace implementation that attaches to the directory with fxtr\_store.toml and exposes essentially the same API as a sqlite namespace, except that it also manipulates the filesystem and uses the filesystem as the source of truth. Also contains the worktree-sync logic which gets called automatically when doing ops
* Worktree-sync command implemented and runnable from the CLI also (driven by a cli script fxtr\_git\_store perhaps)
* Two manual export/import commands runnable from the CLI or python:
  * Checkout export command: take the current synced namespace for the checkout, create a *new* sqlite store in a target location, and then do a copy of everything from the checkout to the new store. New store is a file that represents a snapshot of the state of the store according to the checkout
  * Archive import command: take a snapshot file like the one from the checkout export (or really, any sqlite store we can attach the sqlite python interface to, but with the CLI defaulting to supporting ones shaped like produced by checkout export) and load it all into the *index* namespace, so that now if we did a worktree-sync at the relevant checkout we would be able to find all the things and pull them back into their appropriate state.
  * Idea behind these is that, if you want to share a particular version of your git-backed store, you can let them git clone your tsv files, then also send them an archive that you generated out of band. Then they can import that file, and then use the worktree sync command to attach it to their own git-backed clone. Eventually it would be nice if git push and git pull automate and deduplicate this using packs, but for now it’s fine to have this go out of band.

Then to build out the tighter git integration in the future we would add

* Mechanism for connecting to a “remote namespace arena” over SSH or HTTP or something
  * essentially will need us to bring back fxtr RPC. Basic thing we need is ability to both do RPC and also bridge arenas, so that you must give an arena to send an entity, and you receive entities in an RPC arena. Can also send caps like capnweb. Or maybe it is capnweb? or a thin layer on top. but maybe simpler to start custom, I don't need promise pipelining.
* Custom merge driver to merge .fxtr.tsv files, configured with git in the repo however that works
* pull-sync and push-sync commands that connect over the “remote namespace arena” and directly copy entities to/from the local index namespace and the remote (also index) namespace
* Custom protocol to intercept packs
  * git-protocol-fxtr
  * combines a git URL and a fxtr server URL
  * Runs syncs in both directions as needed
  * With fxtr commands configured so that pull-sync and push-sync also automatically connect to the fxtr server from the URL
