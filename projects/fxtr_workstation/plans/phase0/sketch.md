Overall idea: A multi-client workstation for fxtr, enabling human users and AI assistants to collaborate on data generation and analysis workflows.

## Mental model:

- A single workstation server manages the state of all resourcess
- The server also has a number of persistent stateful _sessions_. Each session is an isolated connection to some resources.
    - A single client may have multiple sessions open. One example of this might be if they have multiple sub-applications open in different panels of a shared client interface.
    - Clients can share sessions, or have distinct sessions from each other. They are distinct by default.
- Clients are (mostly) reactive views on the server-side state (plus very small amounts of purely-local state in local storage) and do not hold significant state in memory. This means you are free to e.g. close and reopen a client and continue where you left off
- The workstation server, however, is dynamic and stateful. It may hold onto long-running processes and in-memory state, especially for services.
    - It tries to offload _data_ storage onto disk whenever possible, but does not attempt to checkpoint all of its state
- There are two kinds of clients:
    - Browser clients are for humans interacting with the system in a browser. Usually these will multiplex over sessions with one session per panel, plus some raw debug views of what else is going on. This is also where most interaction between agents and humans happens. Sessions in a browser client are usually controlled by type-specific UI code that the human has opened; the human usually won't directly manipulate state.
    - Agent clients are for agents interacting with the system over MCP. Usually each agent session has a single workstation session, and it represents all of that agent's work. These are highly dynamic. Sessions in an agent client are usually controlled via the agent running sandboxed code to update the state of the session. The low-level session state is managed by the MCP server and functions mostly as a durable namespace for the agent's dynamic work.
- Despite being used differently, the two client types have the same basic affordances; they refer to the same universe of objects, and can trigger actions and subscribe to their results in the same way. This makes it possible to build components that can be flexibly passed between humans and AI agents, and expose any general-purpose tools to both.

## Workstation server details:

- A workstation server maintains the workstation state.
- Workstation state incudes:
    - Tracked FxtrIDs: IDs that are tracked in the workstation directly. Each has a short ID that can refer to it (first 7 chars of its ID string for d/n/c nodes; full ID string for other nodes).
    - Tracked Services: Service handles that are tracked in the workstation directly. Each has a short ID (default is "s{number}" for some autoincrementing number managed by the workstation)
    - Workstation Configuration: Configuration/preferences for how the workstation should work. Initially empty.
    - Sessions: Persistent, locally-scoped interactive state shared between the workspace and some client. Each session has a UUID and some metadata
    - Connected Clients: Bidirectional live connections to particular clients
        - Usually, each client will control / attach to one or more sessions
        - Technically possible for multiple clients to attach to the same session
    - Attached services: Services that have been externally bridged into the workstation
- What a client has:
    - Each client has a websocket connection to the server
    - Clients are associated on the server with a unique client connection ID
    - Primarily clients send and receive messages about sessions
- What a session has:
    - Each session is associated with
        - an arbitrary JSON object representing its state
        - a sequence of incrementing-integer-indexed "live" slots:
            - job result slots
            - callback notification slots
        - a subset of FxtrIDs and ServiceRef IDs (possibly identified by short ID) that the session is actively using
        - an event-sourced log of things that happened in the session, including both state updates and notifications, with a per-session incrementing event sequence number
            - where notifications refer to the job result or callback notification slot they are for
        - a "last acknowledged" sequence number of the most recent event that has been processed into the state
    - Clients can subscribe to a session:
        - At session start: They receive:
            - the most recent state update and its "last acknowledged" sequence number
            - all notifications that occured after that state update's acknowledgement number
            - the next available live slot
        - Afterward: They receive a stream of:
            - Acknowledgements or rejections of previously-sent state updates for this session by this client
                - Rejected updates indicate that some other state update occured instead and the client needs to retry
            - New state updates received via other connections to this session (not this client) along with their last-acknowledge sequence numbers
            - Result notifications for their open slots
    - Clients can submit state mutations:
        - State mutations are like "ACID transactions" from the client's perspective (durable over the lifetime of the workstation)
        - Each state mutation request carries two identification numbers:
            - A new "acknowledgement" event sequence number: the last message from the server that the client has processed and handled fully.
                - This means that all events before this have been "handled" and do not need to be redelivered. In particular, the expectation is that any notifications that the client needs have already been checkpointed into the state update.
                - This also identifies which external version of state the client was aware of. If the state has been updated since this by some other client, the server rejects this update.
                    - Note that updates to the state by the same client that updated the state last time are always allowed, because the client is assumed to know what state they used last time.
            - A client-side state update ID, generally unique per connection: Identifies this attempt to modify the state.
                - Used for update acknowledgements
                - (Note that this is a general feature of all messages sent by the client, see below)
        - Each mutation contains an update to its mutable state, expressed as a JSON patch
        - Mutations can then also include a sequence of other operations:
            - Add or remove FxtrIDs or ServiceRefs from the state (including adding ones _from anywhere in the workstation_ to support cross-session communication about data out of band)
            - Create a "callback" ref and bind its result to an integer slot
                - The slot MUST be strictly larger than all previously-used slots
            - Load a FxtrID, binding its result to an integer slot
                - The slot MUST be strictly larger than all previously-used slots
            - Invoke a method on a tracked ServiceRef, binding its result to an integer slot
                - The slot MUST be strictly larger than all previously-used slots
                - They can pass as their argument an escaped (similar to capnweb) set of arguments, which can be JSON + can refer to tracked IDs and refs _anywhere in the workstation_ by (short) ID, and can also refer to "the ref representing the sender end of my callback slot {s}"
            - Close a previously open callback slot
        - Note: Assumption is that clients always mutate their state to track what operations they have done. Thus, the server does not tell the clients about the full sequence of operations they did, only about the resulting state. This implies that clients should e.g. store the integer slots they are using and what they are for, and store what IDs they are tracking and why.
    - Client notification contents:
        - State updates from others:
            - The event sequence number of this update
            - The new state + the new acknowledgement sequence number
            - They do NOT receive info on other mutations made, or info about the client that made the update
        - State updates from themselves:
            - The event sequence number of this update
            - The update ID for matching purposes
            - A flag that it succeeded or failed
        - Invocation result notifications:
            - The event sequence number of this update
            - The slot it is for
            - A JSON representation of the result of the call, escaped (similar to capnnweb) to indicate FxtrID and ServiceRef
        - Callback notifications:
            - The event sequence number of this update
            - The slot it is for
            - A JSON representation of a message, escaped (similar to capnnweb) to indicate FxtrID and ServiceRef
- Note on lifetimes:
    - The workstation server is responsible for keeping around all of its tracked FxtrIDs and ServiceRefs
        - By default, all tracked FxtrIDs are first copied into a persistent sqlite store before being delivered as results, then they are attached to a scope attached to that store
        - Each ServiceRef is held inside its own isolated scope to allow independent lifetimes
    - The workstation server also owns all callback refs
        - These are small ServiceRef impls owned by the workstation
        - They get their own service IDs but are attached to the session that is subscribed to them
    - The workstation server is responsible for keeping around the results of calls and callbacks until the clients have a chance to process them
        - This means that any FxtrID or ServiceRef that is either (a) tracked explicitly in a session's state or (b) referenced by a call result or callback result that has not yet been successfully acknowledged by a session as part of a client-triggered mutation, cannot be released
        - Once it is no longer either of these, the workstation can safely release it
- Client websocket multiplexing and session introspection
    - For simplicity requests from a client are multiplexed over a single websocket
    - Workstation allows querying for the list of all sessions and watch for changes to this
    - This can be used by a client to connect to an existing session
    - Client messages can
        - subscribe to a session
        - send session mutations
        - unsubscribe to a session
        - create a session with particular metadata
        - close a session
        - subscribe to the list of all sessions
        - unsubscribe from the list of all sessions
        - request sessions matching particular metadata
        - subscribe to or query the list of tracked IDs and service refs
        - subscribe to or query the list of externally-attached RPC connections and their registered IDs and service refs, along with the connection names and service/entity names
    - Server responses then identify which client message they are responding to, by ID
    - Clients will often multiplex many sessions together. To match this up:
        - Subscriptions to a session identify it by UUID. The ID of the subscription is then used to identify this subscription:
            - Notifications of updates refer back to the ID of the call used to subscribe
            - Mutation messages do not send the whole UUID but instead send the ID of the call used to subscribe (since mutations must be in sync with the subscription sequence numbers anyway)
            - Unsubscriptions refer back to the ID of the call used to subscribe
            - State update responses will refer to both the subscription ID and the ID of the message they are responding to
        - From the perspective of the server, every unique subscription to a session is a unique "connection" even if multiplexed over one websocket. (Thus if you for some reason were to subscribe to the same session twice over the same websocket, you'd receive double the messages, and if you updated from one, you'd receive it back as an acknowledgement over one subscription but as an external update from the other. This should simplify the implementation and also make it easier to avoid tricky edge cases due to e.g. connecting to the same session twice.)
- Attached services
    - You can register a new service via an endpoint separate from the client one, which speaks fxtr RPC
    - This is similar to fxtr_sandboxing's guest connect protocol, but conceptually inverted:
        - The server provides you a workstation service, with a few methods
            - `register_service(self, external_service_name: str, service: ServiceRef[Any]) -> tuple[str, ServiceRef[ReleaseCallback]]`
                - You invoke the register method with a unique service name and a ServiceRef
                - The workstation bridges it out and keeps it alive (beyond the lifetime of the register call); it becomes a service in the workstation
                - The workstation associates this name with its internal service ID, and returns the internal service ID as a string
                - You receive a callback that lets you unregister the service; if this callback is dropped it also automatically unregisters the service (based on a similar design as fxtr_sandboxing's NetworkAuthorizer, see the protocol and token-end-callback system in plans/stage2/2p1_new_rpc_system/stage3_transports.md )
                    - The service is no longer bound by name at this point
                    - If the service is not being depended on by any sessions, it will release the resources
                    - If the service _is_ being depended on by any sessions, those sessions will keep the resource alive, which may keep the connection open unless killed
            - `copy_entity(self, external_entity_name: str, entity: FxtrID | EntityRef[Any]) -> ServiceRef[ReleaseCallback]`
                - You invoke the `copy_entity` method with a unique entity name and an entity, which is copied into the workstation
                - The workstation associates this name with its internal entity short I
                - You receive a callback that lets you release the entity
                    - The entity is no longer bound by name at this point
                    - Other sessions that depend on the entity may keep the data alive in the server
                    - The entity has already been copied so the connection does not need to stay open
            - `get_service(self, service_ws_id: str) -> ServiceRef[OverrideThisTypeBeforeUsing]`
                - This bridges a workstation-tracked service into your scope
            - `get_entity(self, entity_ws_id: str) -> FxtrID`
                - This lazily bridges a workstation-tracked entity into your scope
            - `name_connection(self, name: str) -> None`
                - Names this RPC connection. Mostly for debugging / introspection

## Primitive debug user client:

- Very lightweight self-contained react typescript frontend that connects to the workstation server over a websocket (this can be in a small self-contained package `debug_ui` inside fxtr_workstation and should NOT reference or use anything from the ts folder, which we will come back to later)
- Subscribes to list of RPC connections and shows their metadata + the names and IDs that those connections have bridged into the scope
- Subscribes to list of sessions, shows a list of all sessions with checkboxes
- For checked sessions, subscribes to that session
- For now just a read-only log of the session state, does not expose any mutation ability
- For each session, shows the session as a log of events received
    - State update events show twice: the state update shows right after the position of that update's acknowledgement counter, and the _ack_ of the state update by the server shows at the sequence number of the ack
        - Conceptually the first one is where it was sent according to who sent it, and the second is when it became common knowledge that it had won
    - All events prior to the most recent state update's acknowledgement counter are grayed out
- Also shows a list of all tracked IDs and services

## Agent plugin/MCP client:

- Primary way that updates to the workstation will be driven
- Connects as two things:
    - An attached fxtr service: Used to introduce new data into the system
        - The service is extremely basic: it takes a string key and returns an entity
    - A client: Used to actually operate and manipulate the state of the system
- High level workflow:
    - Agent writes files in its local directory
    - Agent uses plugin/MCP tools to:
        - Run code that can
            - Construct and send entities into its session
            - Manipulate and invoke the entities and services in the session
            - Create callbacks
            - (eventually) Package and ship locally-written code into sandboxes
        - Interrogate tracked objects
        - Monitor for callbacks and invocation results
- Low level principles of operation
    - The agent interfaces with its session state primarily as a simple result queue; it is expected to track the relationships between things itself
    - Essentially, the state of the session is
        - a map, where keys are agent-determined, and values are either (a) references to slots that have not resolved, (b) escaped values of slots that _have_ resolved
        - some extra transient state having to do with
            - new entities being mounted into the scope (specifically, the slot where these will go and how they match up)
            - entities being loaded for printing
        - the set of entities that the session knows about
    - When the agent invokes a call:
        - The code they run may trigger uploading of new entities
        - The server uses its attached RPC connection to register each entity into the workstation under a UUID
        - After receiving this, it schedules the call, unregisters each entity, and gives control back to the agent
    - When the agent reads an ID
        - This triggers a transient request to load that entity
        - The client waits until that request is fulfilled, acks it, then shows it
- Agent facing tools
    - Inspect a tracked ID or service
        - For an ID: loads the entity data, shows it, binds any children to their short ids and tracks them so the agent can inspect them later
        - For a service: loads the entity's type and its context provenance marker
    - Invoke jobs
        - Essentially how this will work is that the agent writes Python commands that execute inside a tightly-restricted sandbox, and which declare what jobs need to be scheduled, kind of similar to how starlark in bazel lets you declare things that need to be built, except that when the script is done executing all of the things declared there immediately begin executing
        - The agents script can import from any locally-defined Python packages and use fxtr2-portable. However it does not get access to any live capabilities. Instead, it gets some special fns:
            - `async def lookup_entity(short_id: str) -> FxtrID` | `async def lookup_entity(short_id: str, type: EntityTypeAnnotation[T]) -> EntityRef[T]`
                - Retrieves the full FxtrID for a tracked entity by its short ID
                - Also tracks this ID in the sandbox's scope. This can allow the agent to do more sophisticated reads of Fxtr data from the sandbox.
            - `def get_service(service_id: str, type: ServiceTypeAnnotation[T]) -> ServiceRefStub[T]`
                - Looks up a service ref for a capability known to the workstation
                - This ServiceRefStub is not actually a ServiceRef tracked in the scope; it is a thin wrapper around the workstation's ID space.
                - The main function of this is to be passed into `schedule_invoke` either as the service or as an arg
            - `def get_id_for_service(ServiceRefStub[T]) -> str`
                - Retrieves the workstation ID of a service
                - Note that all ServiceRefStubs passed to `expose_service` must already come from the workstation anyways. The root scope is not mountable so the script cannot directly bind new services
            - `async def export_entity(slot_key: str, entity: FxtrID | EntityRef[Any])`
                - Requests that an entity should become tracked for this session in the workstation
            - `async def export_service(slot_key: str, service: ServiceRefStub[Any])`
                - Requests that a service should become tracked for this session in the workstation
            - `async def schedule_invoke(slot_key: str, service: ServiceRefStub[T], action: Callable[[T], Awaitable[Any]])`
                - This is type-annotated as giving you what the service resolves to
                - However, it is restricted in form, and is actually called with a proxy object that just records what method call was made, and then requires that exactly one method call was made and that the result was returned directly
                    - so you call it like `schedule_invoke("foo", lookup_service("s13", MyServiceType), lambda svc: svc.foo(bar, baz, qux=qux))`
                - the `T` type is required to be recognized as either UnknownService or a typed service protocol, rather than using the full dispatch path. If typed, we use the same arg-conversion logic of typed_service
                - This enqueues a job with this name as an invocation op.
            - `async def retrieve_result(slot_key: str, result_type: TypeAnnotation | None = None)`
                - Retrieve the result from a successful `schedule_invoke`
                - Can convert the type according to whatever result type you expect
                - Convenience function `result_type_of(cls, method: str)` which gives you the result type for calling a method on a `service_protocol`-decorated protocol; you could pass the method that was invoked to get back a typed version of what was retrieved
                - Note that ServiceRefs in the result will actually be returned as ServiceRef
            - `def forget(slot_key: str)`
                - clear the given slot data so we don't hold it persistently in the session anymore
        - The script runs in a scope that can get access to and load entity data from the workstation (via the workstation's `get_entity` which we bridge into the script). However, it does not imperatively cause any changes; rather, it simply enqueues them. If the script runs successfully, then explicitly exposed entities become tracked, and all invoked jobs are pushed together as a state update
            - Basically the way this works is:
                - Script runs inside a scope where we have bridged in the workstation's get_entity via some sandbox nesting
                - Script executes and logs what needs to be done
                - At the end of the script, all entities passed to export_entity or to schedule_invoke are copied out of the sandbox into the session. The way this works is essentially:
                    - Data is copied out of the script into the MCP process's scope
                    - MCP process temporarily exports that data from its own RPC connection via external entity registration, getting the short IDs
                    - MCP process runs a state update for the session, invoking the calls using the short IDs
                    - MCP process waits for the session to ack the mutation that invoked the call
                    - At this point it can close the entity registrations
                - The actual results coming back are async; the MCP process can just wait to be notified that the methods have completed
    - Monitor for job results
        - This should be automatic and should mostly automatically work as long as the plugin is activated
        - Basic mechanics are that we notify the agent whenever the workstation reports back to us that some invoked job completed, and pass the key of the job that finished
- Agent local filesystem state
    - Assumed to have a folder packages/ which contains a collection of (sandboxable) python packages
    - Also has a `preamble.py` which is injected into globals immediately before any sandboxed execution
    - All packages and the preamble are read-only mounted into the sandbox (ideally via a virtual filesystem to accelerate startup time) in a context where _every_ package can be directly imported (as if an editable dependency of the main script). Premble can directly load from this
    - Eventually, the agent should also be able to bundle up these packages as fxtr entities and ship them as sandboxed spawned services
