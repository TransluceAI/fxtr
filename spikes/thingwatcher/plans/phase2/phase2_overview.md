Now that a basic scaffold of thingwatcher exists, we can focus on adding new features.

(rough sketches, now with detailed plans)
1. switch frontend to use dockview and make the three main view panels (not the timeline) into non-closeable dockview panels. add the ability to open a new panel by right clicking a node or a node link. this puts the node in its own panel even if it is not selected. panel shows the same content as details view. refactor to enable sharing of this as needed
2. add concept of "roots": specific things which are mounted on the watcher with specific names. make a new panel for showing roots and letting you select from them. (each tick will have a particular set of named roots, tracked in DB and queryable via graphql. the roots are stored just as thing keys. roots act kind of like anchors, in that they have a capturer that returns a single thingstate or a thingref. maybe we generalize PauseCapturer to be called AnchorCapturer. but then they are stored in a separate map from name to thing-key, and the map gets updated by calling addRoot and removeRoot)
3. add parsing-out of cbor keys, so that over graphql you can ask for keyJSON and that gives you the JSON object (or null if not json deserializable). then make it so that the frontend shows the keyJSON in the UI (falling back to base64 if null). also update agent docs to mention keyJSON. also make it possible to query by passing in keyJSON. keep shortID and full key base64 as well.
4. add custom fancy renderers, with dynamically compiled component functions derived from dynamic react spike, + dynamic access to our urql client to allow querying for the data of this thing and the things it links to, as well as dynamically triggering triggerable nodes with custom payload logic. location of dynamic react spike will be provided when we start planning this step. will be important to also have a fallback renderer which can be the one that currently exists.
5. add backlinks between things to the details view and thing view panels, outside the custom renderers, at the bottom. this should be a list of other things that point to this thing at the current tick. not accessible to the custom renderer itself. formatted like the current fallback link showing system.
6. add a better system for ownership of snapshots. right now snapshotters can either return states or deltas and then we merge the states that are the same during snapshotting. I'd like to make it so that instead there are two types of snapshotter, there is a StatelessSnapshotter and a StatefulOwningSnapshotter. StatelessSnapshotter returns thing states only, and it is OK if two stateless snapshotters return the same thing state, or if this duplicates with anchor capturer thing states. StatefulOwningSnapshotter is allowed to emit ThingDelta or ThingState, and also it is an error if a StatefulOwningSnapshotter ever emits the same thing key as some other snapshotter or anchor capturer's thingstate. we also store bidirectional maps to let us find what a given tracked object owns (when it has a stateful snapshotter) and what tracked object owns a given thing record (if any), which we will use later. (for now these maps could maybe be used to improve some error messages while snapshotting, if that's easy)
7. add streaming subticks. reserved tick type called "stream", which is not allowed to be emitted via graphql or the normal API. new top-level api `streaming_update(tracked_object)`, which does a streaming tick for just that object. the object must already be tracked and it must have an owning snapshotter associated with it. when we do a stream subtick, we just snapshot the specific object with the streaming subtick. we then check if the most recent tick in the database is a "stream" type. if so, we _overwrite_ whatever was in that tick for this object. if not, we create a new tick that clones the old tick but with "stream" type, and then overwrite into it. essentially a streaming subtick is not immutable, and we can update individual objects in it in a streaming fashion. then use this streaming subtick system in the multi-chunk demo, with separate de-synced streams for the counter and the logger. note that if a thing disappears in a streaming subtick's snapshotter we still remove that thing if it was previously owned by this snapshotter, but obviously we don't remove outputs that are owned by other snapshotters. also it should be allowed to `stream_subtick` on an object that has not yet appeared in a full tick, that's fine, but it does have to be tracked already.
8. add a new route that lets you look at a single thing at a time, and both change the thing and pass args to it by postMessage-ing. use it to build a micro vscode plugin for viewing things related to code you are writing.
9. add some ability for renderers to save persistent state keyed by their thing ID, so that even if the react component re-mounts, we don't lose the state. it only needs to be persistent in the active session. this should be exposed as a state hook `usePersistentThingState(key)` exported by thingwatcher-bindings, maybe requiring them to pass a unique string key to ensure rebinding works. when you open the same thing multiple times though they all share the state. this state should work in both the main view and the embed view. the default is _always_ undefined, and we optimize by removing undefined from the map.

- 21. add "immutable object stores" as a concept to thingwatcher, where you can register such a store, and this then allows us to navigate into immutable content-addressed objects that are served according to a particular protocol.
    - mental model is that an immutable object store is something you can attach to the thingwatcher watcher, and it lazily owns some set of things that are assumed to be immutable / constant over time.
    - if any snapshotter tries to produce thing states that are also in the immutable store, that is treated like a stateless snapshotter conflict. we resolve these conflicts by looking up each thing in the store immediately upon encountering it in a snapshot
    - things owned by an immutable object store are _lazy_; they are not included in the list of active things at any tick, but they can appear in ThingLink or ThingRef.
        - immutable object stores allow you to ask for a ThingState for a given key. they also allow you to directly ask for backlinks to a given key.
        - the graphql server uses this to handle requests targeting them. if we request a thing that we don't have tracked in a snapshot, we also try asking for it in all of the stores, and expect either it to appear in exactly one store, or in multiple but be an identical ThingState.
    - because they are immutable, we don't track them over time, we simply assume that they don't change over time. we assume it is cheap to request things by key repeatedly.
    - in the frontend, we will need a way to track and display things that are not in the things list for a given tick. we'll essentially do this by having a "temporary things set" maintained by the root app, which is a list of other things that we are considering to be active currently
        - any thing that was captured at a given tick is always active. this is like the current set of things we are visualizing
        - any thing that is open in a panel must be active. this means that if we follow a link from a thing to another thing, and the second is found in an immutable store, we can open it in a panel, and at that point it also gets added to the graph and is treated as active
        - other lazy things that are linked to from an active node, or which have a backlink that points to an active node, are NOT automatically in the active set, but they DO show up in the various thing panels and can be loaded into refs etc. if those refs are clicked or dragged into a new panel, they become active and appear in the graph when they have a panel
        - immutable things can be "pinned" at which point they stay in the graph and things list even if their last panel is closed
    - in the frontend, whenever displaying a thing in a panel, we show a small note above the thing indicating where it is from. this could be a list of sources, sources could include "Captured in snapshot at tick {t}" or "Retrieved from store {x}" depending on whether it was a snapshot thing or from an immutable store.
        - for "Retrieved from store" sources, there is a little pin icon no the left, and you can click it to pin the thing which will keep it visible. pin state is shared across all stores but its fine to duplicate the pin icon; usually there will be only one store so it will look normal.

24. Allow async owning snapshotters via streaming ticks
    - (problem: right now ticks need to be sync so that they capture a specific consistent point in time and don't interleave, but some state checks ideally would involve waiting for async ops, so we want to add support for that to the system)
    - StatefulOwningSnapshotter gets a new optional return type
    ```py
    @dataclass(frozen=True)
    class AsyncThingUpdate:
        """(snapshot result that requires async work to compute the final state)

        Attributes:
            immediate_update: (the immediate state of the thing, will be reported as the state of the thing at the current tick, but could indicate that it is pending or stale or being computed)
            async_updater: (async callable that computes the full update to the state of the thing. if it contains ThingDelta, they are applied _after_ immediate_update. results will appear in a streaming tick following the sync tick. this callable will be async-cancelled if another tick() or streaming_update() to this thing occurs; in this case the updates will _not_ apply, so the updater should make sure it does not commit any changes to its own internal snapshotter state until after its last `await`)
        """
        immediate_update: ThingState | ThingDelta | Sequence[ThingState | ThingDelta]
        async_updater: Callable[[], Awaitable[ThingState | ThingDelta | Sequence[ThingState | ThingDelta]]]
    ```
    - watcher class tracks pending async updates with a cancel scope for each async update. the update runs as a task in the watcher's task group, launched inside the tick() or streaming_update(). old task is immediately cancelled if it still exists, prior to calling any of an owning snapshotter's snapshot methods. when an async_updater completes successfully without being cancelled, it pushes its update using the same flow as streaming_update uses, to a streaming tick (but bypassing the snapshotter call and just directly using the result)
    - maybe we refactor watcher to have a separate internal helper that is shared between streaming_update and async_updater codepaths that handles sending out the event
    - add an object that demos this functionality to the demo_multi_chunk demo (which currently uses streaming updates); the new object should NOT use streaming updates but SHOULD use the async_updater with a, say, 5sec delay, and it should append debug messages to its state both in the immediate_update and in the async_updater with matched UUIDs, so that we can tell whether async_updater gets cancelled
